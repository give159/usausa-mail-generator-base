title: 単一HTMLツールを壊さずに更新する — VS Code + Claude Code の手順を仕組み化する方法
2026/11/07 YUKIKO

## この記事でわかること

- 2000行等のHTMLを直すときに、**直した箇所より壊した箇所**を先に見る手順
- 修正後の健全性をスクリプトで判定する方法（タグ・JS構文・外部参照・id重複・関数の消失）
- 試験結果報告書を、判定欄を手で書けない作りで生成する方法

## 対象者
単一HTMLで作っていて、改修作業がうまくいかず悩んでいる方向け
フライン完結で配れるのが単一HTMLの利点ですが、更新のたびに事故が起きやすいという弱点もあります。その弱点を仕組みで潰した記録です。

## 前提

- 環境: VS Code 1.94.0以上 / Node.js v22 / Python 3.12 / jsdom
- 対象読者: 単一HTMLのツールを自分で保守している人
- Claude Code は有料のClaudeサブスクリプション、またはClaude Consoleアカウントで使えます

## 課題：直したところより、壊したところが怖い

単一HTMLツールの修正で本当に怖いのは、直した箇所ではありません。**直したついでに壊れた別の箇所**です。

たとえば、こういう壊れ方をします。

- 閉じタグが1つずれて、そこから下のレイアウトが崩れる
- `id` が重複して、`getElementById` が別の要素を拾う
- 直したい関数の隣にあった関数を、範囲指定を誤って巻き込み削除する

厄介なのは、**どれも静かに壊れる**ことです。`getElementById` は重複した `id` があっても例外を出しません。最初に見つけた要素を返すだけです。画面はだいたい動いているように見えて、特定のボタンだけが効かなくなります。

そして版番号だけが更新され、壊れたまま配られます。

## 考え方：気づけないものは機械に見せる

判断の分け方はいつも同じ基準にしています。

> **これを間違えたとき、人間は気づけるか。**

気づけないならプログラムの担当です。今回の工程だとこうなります。

| 工程 | 担当 | 理由 |
|---|---|---|
| 何を直すか決める | 人 | 直す価値の判断 |
| どこを直すか特定する | AI | 構造を読んで場所を絞る |
| コードを書き換える | AI | 実装は正解が一つに定まらない |
| タグの開閉 | プログラム | 1つのずれは目視では見つからない |
| JavaScriptの構文 | プログラム | 壊れていても画面は途中まで表示される |
| 外部参照が増えていないか | プログラム | オフライン前提が静かに壊れる |
| `id` の重複 | プログラム | 別の要素を拾っても例外は出ない |
| **関数が消えていないか** | プログラム | **巻き込み削除は差分を見ないと分からない** |
| 試験結果の判定 | プログラム | 通っていない試験にOKと書けてしまうため |

## 手順

### 1. 直す前に構造を測る

2000行を頭から読むのは、人にもモデルにも向いていません。**触る行を先に決めてから開きます。**

```bash
python scripts/inspect_html.py tool.html
```

```text
総行数 2030 / 119,885 バイト
刻印   v1.1.2（2026-08-29）
版表記 v0.1, v1.1.2

## ブロック

| 種別 | 行範囲 | 行数 |
|---|---|---:|
| style | L7-L204 | 198 |
| script | L617-L1237 | 621 |
| script | L1238-L1420 | 183 |
| script | L1421-L1885 | 465 |
| script | L1886-L2027 | 142 |
```

関数と行番号、`id` の総数、外部参照の有無も一緒に出ます。

これを作っているときに、自分のスクリプトのバグを1つ見つけました。`</script>` の直後の行から次のブロックが始まっていると、その行を読み飛ばしていたのです。4つあるスクリプトブロックが2つしか出ませんでした。走査位置を1行進めすぎていただけの単純なミスですが、**実ファイルに当てるまで気づけませんでした**。自作の道具はサンプルではなく実物で試すべきです。

### 2. 控えを取る

```bash
cp tool.html tool.bak.html
```

この1行を省かないでください。比較対象がないと、**消えた関数を検出できません**。

### 3. 直す場所を行範囲で伝える

Claude Code に「このツールを直して」と丸ごと渡すと、全文を書き直そうとします。そうなると差分が「2000行変わった」になり、意図した変更と事故を区別できなくなります。

- 良くない: このHTMLのタブ機能を直して
- 良い: `L1421-L1885` の script にある `openTab` を直したい。他の行は触らないで

VS Code 側で1つ設定をしておくと差分が読みやすくなります。

```json
{
  "editor.minimap.enabled": false,
  "files.trimTrailingWhitespace": false
}
```

`trimTrailingWhitespace` を `false` にするのは、**保存しただけで全行に差分が出るのを防ぐため**です。行末の空白が一斉に消えると、実際に直した箇所が埋もれます。

### 4. 壊していないかを検査する

ここが本題です。

```bash
python scripts/check_update.py tool.html --before tool.bak.html
```

```text
✓ 2030 行 / 119,885 バイト / ブロック 5 件 / 関数 44 件
✓ HTMLタグの開閉は整合している
✓ script ブロック 4 件の構文は正しい
✓ 外部参照なし（オフラインで完結）
✓ id 68 件に重複なし
✓ 版表記 v1.1.2
✓ 関数の増減なし
✓ 行数 2030 → 2030
△ 修正したなら、この刻印は無効です。試験をやり直して刻印し直してください
結果: PASS — 試験を実行してよい状態です
```

JavaScriptの構文検査は、`script` ブロックごとに切り出して `node --check` にかけています。ブロック単位で見るのは、**どのブロックが壊れたかまで出したい**からです。

差分の検査で効くのは関数の消失です。実際に試すとこう出ます。

```text
✗ 修正前にあった関数が消えています: slugify
```

外部参照を1行足したときはこうです。

```text
✗ L4: 外部参照が入っています: <script src="https://cdn.jsdelivr.net/npm/x"></script>
✗ 外部参照が 0 件から 1 件に増えています
```

`id` を重複させたとき、版表記を混在させたとき、それぞれ別の指摘が出ます。検査を書くときは、**まず壊したファイルで確実に落ちることを確認**してから、正常系のPASSを信用します。何をやってもPASSする検査は飾りです。

### 5. 試験を5レベルで回す

jsdom で単体・結合・システム・モック・受入を実行し、結果をJSONに落とします。

```json
{
  "単体試験": [
    {"name": "parseTime 正常値", "ok": true, "note": ""},
    {"name": "parseTime 異常値はnull", "ok": true, "note": ""}
  ],
  "結合試験": [],
  "システム試験": [],
  "モック試験": [],
  "受入試験": []
}
```

モック試験でよく漏れるのが「**偽物が失敗を返したとき**」です。クリップボードAPIが拒否されたら代替手段に落ちるか、一時URLを解放しているか。成功したときだけ試すのは、モックを使う意味の半分を捨てています。

### 6. 報告書を生成する

```bash
python scripts/make_report.py --results results.json \
  --target "うさうさイベント指揮所" --file usausa-event-console.html \
  --version 1.9 --out 試験結果報告書_v1_9.md
```

サマリ表、レベルごとの一覧、試験の考え方までを組み立てます。ここで大事なのは、**判定欄は実行結果からしか入らない**ことです。手で `OK` と書けません。書けてしまう時点で、報告書は証拠ではなく作文になります。

不合格が1件でもあると終了コード1で終わり、未通過の項目が報告書の末尾に列挙されます。

```text
## 未通過の項目

以下が通っていません。この状態で刻印してはいけません。

- 結合試験 02: 保存と読込の往復
```

### 7. 版を上げて刻印する

刻印には、刻印時点の中身のSHA-256を含めています。

```text
<!-- USAUSA-STAMP v1.1.2 | 2026-08-29 | gates: UT 21/21, IT 11/11, MT 5/5, AT 7/7 | sha256:32ddd97b… -->
```

版番号だけだと「v1.9 と書いてあるが、刻印後に3回直した」という状態を誰も検出できません。ハッシュがあれば機械的に分かります。

順序に1つだけ注意があります。**版表記を先に書き換えてから刻印してください。** 逆にすると、刻印に記録したハッシュと中身が即座に食い違います。

## つまずいたところ

### 全文置換の誘惑

「ついでに整形しておきますね」で全文が書き換わると、差分が読めなくなります。整形と修正は別のコミットに分けるべきで、同時にやると事故の切り分けが難しく、解決に至るのに時間がかかります。

### 検査が通っても内容は保証されない

検査できるのは**構造と差分**までです。構文が通っていても、動作が間違っていることはあります。そこは試験の役目で、機械が守れる範囲を正しく理解しておかないと、検査に過剰な信頼を置くことになります。

守れるところを全部守ってから、守れないところを人に任せる。順番を逆にすると、人の注意力が形式の確認に消えます。

### 関数抽出は完璧ではない

関数の一覧は行頭の宣言パターンで拾っています。入れ子や特殊な書き方は取りこぼします。「消えた関数」の検出も同じ精度なので、目安として扱うのが正しい使い方です。**限界を書かずに配ると、道具が過信されます。**

## まとめ

- 直す前に構造を測り、**触る行を決めてから開く**
- 控えを取る。取らないと消えた関数を検出できない
- 修正後は「壊していないこと」を機械に確認させる
- 試験結果の判定欄は、手で書けない作りにする
- 刻印にはハッシュを入れ、刻印後の改変を検出できるようにする

決定論はプログラム、非決定論はAI。この線引きを工程ごとに引いておくと、更新のたびに同じ手順で回せるようになると考えております。
